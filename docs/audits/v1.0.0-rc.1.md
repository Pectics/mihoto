## Local gate evidence

On 2026-07-29, candidate lineage through `23e8656` passed:

- `cargo fmt --all -- --check`
- `cargo clippy --all-targets -- -D warnings`
- `cargo check --all-targets`
- `cargo test --all-targets`: 49 unit + 5 CLI-contract tests
- `cargo test --all-targets --no-default-features`: 46 unit + 5 CLI-contract tests
- `scripts/check-system-scope.sh`, `scripts/check-release-workflow.sh`,
  `scripts/check-v1-contract.sh`, and `scripts/test-installer-contract.sh`

The installer contract covered explicit RC selection, latest-stable selection,
mirror checksum provenance, checksum-failure rollback, and unsupported-arch
no-write behavior. The upgrade unit contract covered `v`-prefix semantic
comparison, RC exclusion, and exact checksum lookup. These are local evidence,
not replacement evidence for a GitHub release or a real host lifecycle.

The first pushed candidate CI run
[`30457623422`](https://github.com/Pectics/mihoto/actions/runs/30457623422)
failed at its pinned Rust 1.88 Clippy gate before later jobs ran. The failure was
seven pre-existing `uninlined_format_args` diagnostics in config, init, core,
Mihomo-resolution, and timer messages; it was not a behavior or test failure.
Candidate commit `2a10e7f` makes only those formatting substitutions. It was
verified locally with installed Rust 1.88.0 using format check, strict Clippy,
and all 49 unit plus 5 CLI-contract tests. The replacement remote CI run is
pending after this record is pushed.

The replacement run passed pinned-toolchain format, Clippy, compile, both test
matrices, and the installer check, then exposed a second CI-environment defect:
GitHub's Ubuntu 24.04 runner has no `rg` executable, while three contract
scripts assumed it. Commit `c43a2e5` replaces those script-internal searches
with portable `grep`; local syntax and contract checks pass. The next remote CI
run, [`30458567156`](https://github.com/Pectics/mihoto/actions/runs/30458567156),
passed all gates in 2m55s. GitHub also emitted a non-blocking Node.js 20
deprecation notice for the pinned checkout/cache actions, while forcing those
actions to Node.js 24; it did not affect the run or product evidence.

### `pectos` execution on 2026-07-30

Evidence commit
[`67c9f1b`](https://github.com/Pectics/mihoto/commit/67c9f1b5739340fec9aa12c5bb7e1a1c5b9f519c)
records a physical Ubuntu 26.04 x86_64 run against candidate `8e9b748`. The
repository systemd and TUN harnesses passed, as did init, idempotent init,
permissions, capabilities, reboot restoration, component updates, apply,
timer execution, and final host cleanup.

The run correctly failed the candidate for two independent reasons:

- The supplied GUI-exported profile contained one Shadowsocks node, two
  groups, and 558 rules but no standalone DNS settings. Traffic entered the
  TUN interface, but neither ordinary DNS nor the single-node Japanese egress
  succeeded. This is not evidence that the Mihoto TUN lifecycle failed; it is
  evidence that the supplied profile was not a working standalone Mihomo
  configuration and that the requested proxy journey remains unproven.
- A YAML-valid but Mihomo-invalid configuration was persisted by
  `mihoto update --config`. The command returned success and
  `mihomo.service` entered a restart loop. The operator atomically restored
  the known-good config, recovered the service, and stopped further lifecycle
  tests as required for a P0.

The remediation lineage starts with RED commits `fa05bc7`, `106fbb7`, and
`35a7fff`. GREEN commits `2ac52e2`, `0f9c0b8`, and `eb601a1` validate staged
configuration with the real Mihomo core, restore the previous config after an
unhealthy restart, reset the failed unit, and reject restart-loop false
positives by observing `NRestarts`. A post-remediation physical-host rerun is
not part of this RC evidence.
